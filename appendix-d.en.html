Appendix D. Public Implementation, Statistics, and Resources

D.1 Public Implementation and Statistical Rules

The experiment code is public. Raw experimental trajectories, training logs, and model checkpoints are not distributed with this report.

Task Generation and Environment Replay

AskAct-EvalRL publishes task generation, simulated environments, evaluation, trajectory replay, and training interfaces. The report uses commit f30851b894d9c52aab8a15edabf883ce4088fc78.

Within the public repository, askact/registry.py and the environment modules define tasks, askact/splits.py defines data partitions, askact/evaluator.py computes behavioral fields, and askact/replay.py implements trajectory replay. Training interfaces are in training/, and analysis tools are in tools/.

The fixed code retains historical explanatory comments. The local-discount explanation of GiGPO in askact/webshop_reward.py should be read with the complete advantage calculation in Section 8.2. The old same-prefix description in research/tools/webshop_intervene.py is corrected by the actual treatment protocol in Section 7.1. The state-anchor comment referring to blocked writes should likewise be read as all actions with blocked_reason, as defined in B.2. The code files remain unchanged.

With Python 3.12 or later, run the rule-based policy from the repository directory:

python -m askact.run_suite --agent rule

This command generates rule-policy evaluation results. Readers who run a model themselves can use the public replay implementation to check their own generated trajectories. The following sections document the report's statistical rules and numerical index.

Two Ways to Compute Interaction-Signature Results

The interaction-signature check (signature_match) compares the trajectory's clarification, confirmation, and terminal action against the task requirements. Results can be aggregated directly from evaluation output or recomputed by replaying the trajectories.

Aggregate per-task results.

Select the relevant tasks from tasks in the evaluation summary, count records whose signature_match is true, and retain the IDs of the passing tasks. For example, this Python code counts an already selected set of tasks:

passed_task_ids = [
    row["task_id"]
    for row in selected_tasks
    if row["signature_match"]
]
signature_match_count = len(passed_task_ids)

When aggregating all tasks, compare the count with the summary field metrics.signature_match_count. Retaining task IDs also lets us check whether two models pass the same tasks.

Recompute after replay.

Reconstruct each task from the trajectory's domain and task_id, restore the request template specified by surface_id, and execute the recorded actions in a fresh environment.

observed_signature extracts accepted clarification fields, whether confirmation was requested, and the realized write, abstain, or no-op terminal from the replayed trace. expected_signature constructs the required signature from the task rules. The trajectory passes when the two functions return equal values. (GitHub)

The default python -m askact.replay command checks the nine evaluation fields and the trace hash. Recomputing the signature additionally requires calling the two functions above on the replayed result.

Pre-Write Policy Lookup

For email tasks requiring a sharing-policy lookup, we scan the recorded actions for the first retrieve_sharing_policy call and the first call to either create_draft or send_email. A write attempt counts toward this position even if the environment blocks it.

Each trajectory receives 1 or 0 according to the table. The rate divides the number receiving 1 by the number of eligible tasks in the evaluation.

Calls in the trajectory Count
Lookup precedes the first write attempt 1
Lookup occurs, with no write attempt 1
First write attempt precedes lookup 0
No lookup, regardless of whether a write is attempted 0

A trajectory with a lookup but no write can receive 1 because the task may require stopping after checking the policy. For example, ten SFT #1 trajectories in the two-tool email test end legally without writing, having already queried the sharing policy. Together with the other 50 trajectories that query before writing, they yield 60/60. SFT-GRPO #1 yields 0/60. For GRPO #1, 58 trajectories satisfy the rule and two lack the lookup, yielding 58/60.

Premature action (premature_action) and evidence sufficiency at write time (evidence_sufficient_at_write) use the evaluator's judgments directly. These fields check whether write attempts satisfy the action conditions specified by the task, while the pre-write lookup statistic checks the order of the tool calls above. With no write attempt, premature action is false, and evidence sufficiency at write time may be null.

Recomputation rules for WebShop output

Prompt groups and tied groups. Read rows from the evaluation file and group records by task goal (goal), with eight trajectories per group. A group is tied when its highest and lowest returns differ by less than 10−910^{-9}10−9. For these evaluations of the external correction, its control, and VPR, excluding groups whose common environment return (env_reward) is 0 or 1 leaves the intermediate tied groups.

Repeated action sequences. Compare the actions arrays of all eight trajectories in a group. Count repetition only when the action order and every action string match exactly. The comparison retains arguments and is case-sensitive.

Required-option matching rate. Within intermediate tied groups, sum the matched required options (options_selected) and divide by the sum of required options (options_required):

Required-option matching rate=Total matched required optionsTotal required options. \text{Required-option matching rate} =\frac{\text{Total matched required options}}{\text{Total required options}}. Required-option matching rate=Total required optionsTotal matched required options​.

For example, the control model in C.2 matches 735 required options out of 2,024 required by the tasks of these trajectories, giving 36.3%.

Share of trajectories matching no required option. Again starting from intermediate tied groups, retain trajectories with options_required > 0 and compute the share with options_selected = 0:

Complete required-option omission rate=Trajectories matching no required optionTrajectories requiring at least one option. \text{Complete required-option omission rate} =\frac{\text{Trajectories matching no required option}}{\text{Trajectories requiring at least one option}}. Complete required-option omission rate=Trajectories requiring at least one optionTrajectories matching no required option​.

For the control model in C.2, this share is 713/1,352, or 52.7%. This statistic counts trajectories; the preceding statistic counts options.

Task Matching Across Text-Treatment Conditions. For each text treatment, match the star-rating reference run and treatment run by goal. Retain pairs only when the task has output under both conditions and the treatment-specific fired condition holds. This field checks whether the specified intervention actually fired.

Then compare the saved purchase Boolean:

control["bought_target"] != treatment["bought_target"]

Each run assigns its own target, and some paired targets differ in §7.2. This comparison checks the Boolean for purchasing each run's own target. Complete purchased-product identities and prefix consistency are separate record checks.

Divide the number of pairs for which this comparison is true by the eligible pair count for that treatment to obtain the change rate of this purchase Boolean. Eligibility is determined separately for each treatment, so denominators can differ.

Validation and Post-Training Evaluation

Both GRPO routes use 48 held-out tasks with changed people and files for validation. Each task uses six request templates, giving 288 inputs. Validation runs once before training and every 12 steps thereafter. Each input produces one trajectory with do_sample=false and temperature 0.

The task-level evaluations reported in Chapters 3–5 use the first request template. Each model runs once on each task at temperature 0, with a limit of 1,024 tokens per model response. SFT #1 undergoes capability evaluation after training.
