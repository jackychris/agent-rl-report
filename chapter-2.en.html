Chapter 2. Ask-or-Act Tasks and Evaluation

2.1 Interaction Modes and Action Chains

Ask-or-Act checks whether the model can use the information currently available to decide whether its next step should obtain more information, carry out the request, or stop. This section defines the behavioral relations required by the tasks. Section 2.2 explains what the nine evaluation fields and interaction signature mean; Chapter 6 uses separate trajectory checks to measure pre-write lookup and the passing of returned identifiers.

For example, a user asks the model to send a budget file. If a lookup returns one suitable recipient, the model can proceed with the sending task. If it returns two candidates with the same name, the model first needs to ask which recipient is intended. The business goal stays the same, while the lookup result changes the correct next step.

The information available to the model before it acts at step ttt is

ht=(o0,a0,o1,a1,…,at−1,ot). h_t=(o_0,a_0,o_1,a_1,\ldots,a_{t-1},o_t). ht​=(o0​,a0​,o1​,a1​,…,at−1​,ot​).

Here, o0o_0o0​ is the initial request, and later observations come from tools, the simulated user, or the environment. The model can act only on these observations and cannot read the environment's hidden state directly.

Six Interaction Modes

Mode Action When to use it Failure
Retrieval retrieve_* Information required to complete the task is available only from the environment. Failing to obtain the information from the correct source before acting.
Clarification ask_clarification(field) Required information is missing and cannot be determined from tools or existing context. Guessing when the user should be asked, or asking when no clarification is needed.
Confirmation request_confirmation User approval is required before changing the environment state. Acting without approval or ignoring a refusal.
Action A world-specific state-changing action The required information and authorization have been obtained, and the request requires a state change. Wrong arguments, premature action, omission, or duplication.
Abstention abstain(reason) A rule forbids action, a prerequisite is absent, or the user refuses authorization. Abstaining when action is required, or continuing when the model should stop.
Termination finish The request has been resolved. Terminating before the task is resolved.

Tasks do not pass through these six modes in a fixed order. The same action may be correct in one task and wrong in another, depending on the information the model has obtained and the task requirements at that point. Ask-or-Act therefore checks whether the model takes the correct next step under the correct conditions.

Paired Tasks That Change One Condition

Each capability test contains a pair of tasks, shown as the first and second conditions in the tables. The two tasks use the same entities and request while changing one condition that affects the correct next step, such as replacing one candidate with two. The difference in model behavior between the tasks can therefore be tied to that change.

The action chains below retain only the steps directly affected by the changed condition; unrelated reads are omitted. A correct chain shows where the model should begin acting differently, while a failure chain shows the earliest observable error. write! denotes a state-changing action in the current world. The exclamation mark indicates a state change and is not part of the actual action name. Names such as retrieve_identity denote the corresponding read tool.

Recovery After a Failed Retrieval

When the first retrieval does not return the required information, the model must use that result to decide its next query. The three tests below cover repeating the same query, reformulating it, and reading the next page, while recording where the next query's arguments come from. The action chains use the email world as an example. Other worlds implement the same relation with their corresponding tools.

The current evaluation covers these three capabilities differently. Query reformulation can be checked directly from the saved actions and tool returns. There is no corresponding evaluation field for whether an exact retry reused identical arguments or whether pagination exhausted all pages. A model can therefore skip the second page, complete the task by another route, and still receive task_success=true.

Action Timing

An action is correct only after its prerequisites have been satisfied. Before requesting confirmation, the model must have identified the target and know that the task requires confirmation; before writing, it must have obtained the required information and authorization. Acting before these conditions are met is premature, while failing to act after they are met is an omission. If a task requires an action, terminating early or entering the wrong branch is recorded as failing to complete that action.

Action Order

Ask-or-Act specifies a set of rules that correct behavior must satisfy for each task; this report calls them the Oracle rules. They constrain only actions with dependencies and do not require the model to copy a fixed reference trajectory. This distinction determines which changes in order count as errors: independent reads may be exchanged, while an action that uses the result of a query must occur after that query. A trajectory must also select the branch supported by returned content, avoid forbidden actions, and use arguments from the correct sources.

2.2 The Ask-or-Act Experimental System

Ask-or-Act is a deterministic simulated task system for testing whether an agent obtains the information required to complete a task and acts at the appropriate time. Each task fixes the tools available to the model, the initial environment state, and the rules for valid behavior.

Five simulated worlds and task scale

Ask-or-Act contains five simulated worlds. Each world includes the 13 paired capability tests described above and adds task changes specific to its purpose. The table below reports the tools, task count, and measurement purpose of each world separately.

Each capability test contains two task branches. Each branch is instantiated with 10 different sets of task objects, such as names and files. The 13 core capabilities therefore produce 13×2×10=26013\times2\times10=26013×2×10=260 tasks. Each additional world-specific group of three tests adds 3×2×10=603\times2\times10=603×2×10=60 tasks.

payments 320 Moves the core tasks into a payment workflow. The added tasks retrieve an invoice amount and an approval threshold, then select direct payment, payment after confirmation, or stopping. The first 260 tasks test domain and interface transfer. The additional 60 test whether the model can combine information returned independently by two tools.

The payment and scheduling worlds each add three relations, and the two email variants each add nine. Ask-or-Act gives the model 25 callable tool functions. Fifteen query the environment, six change environment state, and four let the model ask the user for clarification, request confirmation, stop without acting, or finish the task. Each call contains a function name and its arguments, such as retrieve_files(query="budget") or send_email(recipient_id="u17", file_id="f3"). Appendix A gives the complete function signatures and returned fields.

Email tasks use six request templates while keeping environment facts and scoring rules fixed. Some templates also add contextual cues, such as “has not received it yet” or “the one we discussed last time.” These tests examine the model's response to request wording and its cues. Appendix A.1 lists all six templates.

Task rules and evaluation

The Oracle rules defined in Section 2.1 are fixed when each task is generated. The environment executes the model's tool calls in order and records the complete trajectory, which the evaluator uses to check the task outcome and execution process. Different call orders can pass as long as the required action dependencies are satisfied.

We ran the rule policy in the source on the 260 tasks in the base email world. It selects actions from prewritten rules and is not trained. The policy completed all 260 tasks. All 130 task pairs matched their respective conditions, and no premature actions or policy violations occurred. This confirms that the task requirements and evaluation rules in the base email world can be satisfied together.

Tool calls and environment changes

At each step, the model generates a tool-function call, such as retrieve_files(query="budget"). The system first parses the function name and arguments. Output that cannot be parsed is not executed and leaves the environment unchanged. After a call is parsed, the environment checks its arguments, executes the function, and returns the result to the model.

The evaluator checks separately whether a tool call was parsed, whether it was executed, and whether it produced the result required by the task. A query that returns no target or a write to the wrong object does not complete the task.

The environment also maintains a fact ledger for facts treated as known by the executor. Ledger updates and model-visible observations are stored separately. For example, file clarification in the email environment can return only a file ID while updating the ledger with that file’s sharing rules. The executor uses these rules to check send conditions; the model can call retrieve_files with the file ID to read the sharing rules in its response. In this example, the executor and model obtain the rules at different steps.

For example, if a request gives only an ambiguous name, guessing the correct contact does not complete the required clarification. The evaluator checks action conditions using the clarification calls, user replies, and fact ledger associated with the trajectory. Chapter 6 separately checks trajectories by comparing the owner identifier returned by a group query with the argument actually used in the subsequent member query.

Violations and Omitted Write Attempts

During evaluation, any tool call that is successfully parsed and sent to the environment counts as an attempted action. The attempt remains part of the record even if the environment blocks it. For example, if the model tries to send an email before obtaining user confirmation, the attempt is recorded as premature even when no email is ultimately sent.

Conversely, if the model never attempts an action required by the task, the violation count may still be zero. Because the action was not completed, the corresponding objective is recorded as unmet.

The reward adapter separately uses failed_to_act to identify an omitted write attempt. On a task that requires writing, this Boolean is true when the trajectory contains no write attempt; an attempt blocked by the environment makes it false. This check distinguishes no attempt from a failed attempt, rather than measuring coverage of all action opportunities.

A separate SFT run (sft-targeted192) provides an example. We evaluated this model on 260 email tasks using greedy decoding (T=0T=0T=0), saving one trajectory per task. On every task, it followed the same action chain:

retrieve_outbox × 16
→ finish

That is, it queried the outbox 16 times and then stopped without attempting a write. policy_violation and premature_action were therefore both 0/260, while task success was only 10/260 (3.8%). On tasks that required a write, ending without attempting it did not add a violation, but the task still failed.

Trajectory replay, model inference, and retraining

Replaying a saved trajectory

Deterministic replay starts from the saved task conditions and tool-call sequence. The environment executes those calls again in their original order, and the evaluator recomputes the nine behavioral fields. Replay does not run the model or generate new actions. As long as the task, environment code, and action sequence remain unchanged, the replay result is fixed.

If the corresponding reward configuration is also available, replay can recompute the trajectory reward. Without that configuration, it can recompute the behavioral fields but cannot recover the reward used at the time. Appendix D links to the public implementation.

Rerunning the model

When a saved trajectory is replayed, its action sequence is already fixed. Rerunning the model requires restoring the original model and inference conditions so that the model generates each action again.

We ran the Ask-or-Act evaluation twice under the same conditions without random sampling. About 2% of complete trajectories differed between the two runs, and the task-success rate differed by about one percentage point. One possible cause is that batch composition affects token selection when probabilities are close. For changes of this size, the specific tasks and run conditions help locate the source of the difference.

Retraining the model

Retraining starts from the original initialization and updates the model again using the saved training data and conditions. The public source contains the Ask-or-Act tasks, environments, and evaluation implementation. Appendix D.2 lists the training configurations for the three routes.

2.3 Generalization Tasks

The generalization evaluations separate changes within email from transfer across domains. The former test adaptation within a familiar application. The latter apply action requirements trained in email to payments and scheduling, testing whether the learned capability depends on email-specific entities and tools.

Changes Within Email

Changing People and Files

This test preserves the original task requirements and changes only the entities involved. For example, a training task asks the model to send a report to Zhang Wei, while a test task asks it to send a data table to Wu Min. Both the names in the request and the corresponding contact and file records in the environment change. The model must find the new entities.

If the training task requires recipient clarification, the test task still requires clarification. The same tools retrieve contacts and files, and the file lookup still returns the sharing rules. The model can follow the procedure it has learned, selecting the correct entities from the query results.

This test asks whether the model's procedure is tied to the particular people and files seen during training.

Combining Clarification and Confirmation

This test changes which steps must be completed within one task. Training separately demonstrates recipient clarification and confirmation before sending. The test contains 10 clarification-only controls and 10 composition tasks requiring clarification followed by confirmation. The chains below compare the composition task with the two training task types.

Training task: recipient is ambiguous
Query candidate contacts → Clarify the recipient → Send

Training task: sending requires confirmation
Identify the recipient → Request confirmation → Send after user acceptance

Composition test:
Query candidate contacts → Clarify the recipient
→ Request confirmation → Send after user acceptance

The tools and individual requirements have all appeared in training. What is new is that both requirements must be satisfied in sequence within the same task. Sending immediately after clarification, or requesting confirmation to send before the recipient is resolved, fails to execute this combination correctly.

Changing Information Sources and Decision Rules

The two-tool test changes the information the model needs to decide how to act.

In the original tasks, retrieve_files returns the file information together with whether sending is permitted and whether confirmation is required. The two-tool tasks no longer supply those two conclusions directly: the file lookup returns file size, while retrieve_sharing_policy returns an approval threshold and a hard sharing limit. The model must obtain both results and compare the numbers to decide whether to send directly, request confirmation, or stop.

Original task:
Query the file → Obtain the sharing rules → Act according to the rules

Two-tool test:
Query the file → Obtain the file size
Query the sharing policy → Obtain the approval threshold and hard sharing limit
→ Compare the size with the thresholds → Decide how to act

Finding the correct file is now insufficient to decide whether sending is permitted. The model must recognize that policy information is still missing, call another tool, and make its decision from both returns. Following the original procedure of proceeding to send after the file lookup can lead to premature action.

Changing people and files therefore tests whether an existing procedure applies to new entities; composition tests whether familiar requirements can be executed together; and the two-tool test examines whether the model adjusts when information sources and decision rules change.

Cross-Domain Transfer: Payments and Scheduling

After the people and files in an email task change, the model still uses email tools to complete a sending task. We also use payment and scheduling tasks to test whether capabilities trained on email apply to new applications.

These tasks preserve the same action rules. For example, an ambiguous email recipient requires clarification, as does an ambiguous payee in a payment task. The model must use payment tools to find the payee and make the payment after clarification. This tests whether the model applies “clarify an ambiguous target before acting” to new entities and tools, beyond proficiency with the steps of email tasks.

The following three action chains correspond to tasks with an unambiguous target, permission to act, and no requirement for user confirmation. The model follows the same action rules but uses each domain’s tools to retrieve information and carry out the operation.

Email
retrieve_files       Find the file
→ retrieve_contacts  Find the recipient
→ send_email         Send the email
→ finish             End the task

Payments
retrieve_payees      Find the payee
→ retrieve_invoices  Find the invoice
→ retrieve_ledger    Query ledger records
→ retrieve_payments  Check whether payment already exists
→ submit_payment     Submit the payment
→ finish             End the task

Scheduling
retrieve_agendas     Find the agenda
→ retrieve_members   Find the participant
→ book_session       Book the session
→ finish             End the task

Additional Dependencies in the New Domains

The base payment and scheduling tasks test whether the same action requirements transfer across domains. Two further task sets add dependencies within the new domains, testing whether the model combines retrieved information to make a decision or uses it in a subsequent call.

The base payment tasks directly tell the model whether payment is allowed and whether confirmation is required. We add numerical comparison by having the invoice lookup return an amount and the policy lookup return an approval threshold and a hard payment limit. The model must combine information from both tools to decide how to act.

For example, an invoice amount of 80,000 falls between an approval threshold of 50,000 and a hard payment limit of 200,000, so user confirmation is required first.

retrieve_invoices(...)
→ Returns invoice amount 80,000

retrieve_policy()
→ Returns approval threshold 50,000 and hard payment limit 200,000

Compare: 50,000 ≤ 80,000 < 200,000
→ request_confirmation()
→ submit_payment(...) after user acceptance

These tasks introduce both an unfamiliar payment application and a new numerical comparison requirement. Poor performance may reflect unfamiliarity with payment tools or a failure to combine information from the two queries correctly. To break this problem down further, we designed two-tool tasks in the familiar email domain. They require comparing file size with sharing thresholds to test whether the model can make the same kind of judgment in its original application.

The base scheduling tasks name the participant in the request, so the model can query by name directly. Of the 60 additional paired tasks, 30 retain the name and 30 specify only the owner of a group. The latter require a group query followed by a member lookup using the returned owner identifier.

For example, if the group query returns owner_handle=h7, the subsequent member query must use handle=h7.

retrieve_groups(query=group_description)
→ Returns owner_handle=h7

retrieve_members(handle=h7)
→ Retrieves the corresponding member information

retrieve_agendas(...)
→ book_session(...)

These tasks test whether the model uses information returned by an earlier step to construct its next tool call. The payment tasks require combining two returns to make a decision; here, one query's result must be passed into another query.
