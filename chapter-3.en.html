Chapter 3. SFT Training and Generalization

3.1 Training and Holdout Tasks for SFT #1

We first perform nine SFT updates on 192 demonstration trajectories constructed from the task rules, training the model on the basic Ask-or-Act procedure. The resulting SFT #1 also serves as the starting point for SFT-GRPO #1.

The training data separately demonstrate how to clarify the recipient and how to request confirmation before sending. We use two task sets to test whether these capabilities transfer: one changes only the people and files; the other pairs clarification-only tasks with tasks requiring clarification followed by confirmation. The chains below show the two training examples, the entity-change example, and the composition example.

3.2 Task Performance of SFT #1

We run the initial Instruct model and SFT #1 once on each task. The results are shown below.

Changed people and files (48) 41/48 → 44/48 30/48 → 36/48

The model already completes most tasks before training, but often fails the signature check on clarification fields, confirmation, and terminal effect. After SFT, the number of training trajectories matching the interaction signature rises from 72/192 to 146/192. The same count rises from 9/20 to 20/20 on the clarification–confirmation paired test. Changes on the tasks with changed people and files are smaller: task completion rises from 41/48 to 44/48, while signature matches rise from 30/48 to 36/48.

3.3 Supervised-Demonstration Construction

This experiment tests how changing request templates and demonstration order affects SFT performance on original and transfer tasks. The same task can be phrased as “Send the latest report to Zhang Wei” or “Zhang Wei still has not received the latest report; please send it.” The latter adds a non-delivery cue while environment facts and scoring rules stay fixed. Contact and file lookups are independent, so querying the contact first or the file first both satisfy the task rules. We combine request templates and query orders in four supervised datasets constructed from the same 192 tasks. In each training run, each task is seen about eight times over about 24 updates. After training, we evaluate 320 tasks: 260 original tasks covering 13 capabilities and 60 tasks that require combining information returned by two tools.

For comparison, Instruct completes 215/260 original tasks and 39/60 two-tool tasks; SFT #1 completes 242/260 and 50/60, respectively.

Selecting Generated Trajectories

Another SFT dataset consists of correct trajectories generated by the model itself. The experiment notes report eight runs per original task and 1,458 retained trajectories that both complete the task and follow the required action order. The evaluation summary in those notes states that, after training on these trajectories, the model still completes the original tasks. The filtered dataset contains procedures from the original tasks; the new relations required by the tests are absent from it. This result is retained as a historical summary in Appendix C.1.

We also combine these 1,458 original-task trajectories with the original rule-generated demonstrations and run SFT again. Both sources contain query and write actions, but neither demonstrates the new order required by the transformed tasks. The trained model produces both actions but still attempts a write before querying on the transformed tasks.

Alongside filtering the model's own trajectories, we asked GPT-5.1 to rewrite complete action sequences for the 192 training tasks evaluated with GRPO #1. Its input included the original trajectory and actual tool returns, without a rule-constructed demonstration answer. The rewritten sequence was executed in the deterministic environment and checked for suitability as supervision. The numbers below come from the historical experiment summary.

Selection rule Rewrites passing
Task completion only 143/192
Task completion and execution requirements 26/192

Strict selection also requires correct confirmation and no policy violation, premature action, unnecessary question, or unintended side effect. Of the 143 rewrites that complete the task, only 26 also pass these checks. Across all 192 rewritten trajectories, the experiment notes record 145 cases of incorrect or unnecessary confirmation and 38 cases of premature action; error categories may overlap.

This result informs demonstration selection. Filtering only for task completion admits trajectories with confirmation and action-order errors. If those orders are part of the behavior being taught, the selection criteria need the corresponding behavioral checks.

Cross-Domain Performance After More Training

The payment and scheduling tests use the model trained for two epochs on this section’s dataset combining request-wording and query-order variation. Arrows show the change from the initial Instruct model to that SFT model.

With the basic rules preserved, the model completes more payment and scheduling tasks, including every scheduling task. However, fewer trajectories match the interaction signature in either domain.

With numerical comparison added, the model completes only 3/60 payment tasks. With argument passing added, it completes 30/60 scheduling tasks. Both results are below the initial Instruct model. Compared with the earlier SFT #1, this training recovers completion rates on basic cross-domain tasks, while performance under the added requirements remains poor.

Generalization After SFT

SFT #1 improves performance on both the original tasks and the two-tool tasks. With further demonstration variation and training, performance on the original tasks improves, but the gains on the two-tool tasks do not persist.

All three models trained with different request versions or legal query orders complete every original task, but only 10 or 11 two-tool tasks, below Instruct's 39. Longer training does not restore pre-write lookup either.

Across domains, email SFT does not consistently improve capability. SFT #1 lowers completion rates on basic payment and scheduling tasks. Using more varied demonstrations and training for two epochs recovers basic-task completion, but fewer trajectories match the interaction signature than with the initial Instruct model. Performance also remains poor when numerical comparison or argument passing is added.

The numerical payment tasks are an unusual exception for SFT #1. Basic-payment success falls from 226/260 to 207/260, while success on tasks with added numerical comparison rises from 28/60 to 50/60. Inspecting the trajectories shows that the model attempts to submit a payment before querying the policy on all 60 numerical tasks. It completes more tasks where payment is allowed, while failing all ten tasks where the amount exceeds the hard limit prohibiting payment. The success increase mainly comes from more reliable execution of the payment procedure; the required policy lookup still occurs after the payment attempt.

To separate the effects of an unfamiliar business domain and numerical comparison, we place the same kind of comparison in the familiar email domain, with file size and the sharing threshold returned by separate tools. Both task sets require combining information from two queries, but SFT #1 follows markedly different action orders.

Test Instruct task success SFT #1 task success Instruct premature action SFT #1 premature action
Numerical payment tasks 28/60 50/60 35/60 60/60
Email two-tool tasks 39/60 50/60 48/60 0/60

Back in the email domain, the same model queries the sharing policy before writing on 50 tasks and queries without writing on the other ten. All tasks satisfy the pre-write lookup condition. Here, improved task success accompanies improved query order. With further demonstration variation and training, performance on the original email tasks continues to improve, but this gain does not persist.

One possible explanation is that further training increases reliance on demonstrated procedures. In the original email tasks, the file lookup already supplies the sharing rules, so the demonstrated order completes the task. If the model follows the same procedure after the rules move behind another tool, it attempts a write before obtaining them. This explanation locates the generalization difference in adaptation to changed information sources. Later sections examine tool discovery, call timing, and the effect of returned content separately.

These results show two levels of generalization differences. Limited SFT improves query order within the email domain while premature action persists across domains. With expanded training, even adaptation to a new information source within email deteriorates. Later sections vary the information source, query cues, and returned content to further separate these behavioral changes.
