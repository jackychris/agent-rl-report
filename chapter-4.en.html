Chapter 4. SFT-GRPO: Behavioral Change During Continued Training

4.1 Original Tasks and Cross-Domain Tests

We continue GRPO from SFT #1 in Chapter 3 to examine how reinforcement learning changes the capabilities the model has already learned. Training uses the same 192 original email tasks, each with four request formulations, giving 768 inputs. Whereas SFT supplies complete demonstrations, these inputs contain only the system prompt and user request. The model generates the subsequent tool calls, and the resulting trajectories are scored using the baseline reward defined in Chapter 2.

Each training batch contains 32 inputs, with eight trajectories sampled per input at temperature 1.0. We compute GRPO advantages from the rewards of the eight trajectories sharing an input and update the LoRA parameters. Each epoch comprises 24 training steps, giving 120 steps over five epochs. This chapter compares SFT #1 before continued training with SFT-GRPO #1 at the end of the fifth epoch. Key hyperparameters are listed in Appendix D.2.

During training, we check model performance on the 48 tasks from Chapter 3 with changed people and files. Each task is instantiated with the six request templates in Appendix A.1, giving 288 validation inputs. Four of these templates are also used for training; the other two are used only for validation. We validate once before training and then every 12 training steps.

After training, we compare SFT #1 and SFT-GRPO #1 on the evaluation tasks from Chapter 3. The table below covers the 192 training tasks, the 48 tasks with changed people and files, and the 20 clarification–confirmation paired tasks. Evaluation uses the first request template in Appendix A.1 throughout, with each model run once on each task.

Continued training reduces the number of original paired tasks with premature write attempts.

Continuing GRPO from SFT #1 here reaches 50/60 and 37/60, respectively. Both routes restore basic cross-domain completion, while their results under the added requirements differ substantially.

On numerical payment tasks, trajectories matching the interaction signature increase from zero to 27/60. Although argument-passing scheduling performance recovers somewhat, success remains below Instruct's 52/60.

4.2 Action Order in Two-Tool Tasks

We compare SFT #1 and SFT-GRPO #1 on the same 60 two-tool tasks from Chapter 3 to check whether the model still queries the sharing policy before writing after continued training.

We use the pre-write lookup definition from Chapter 1. Here, the lookup is retrieve_sharing_policy, and a write is a create_draft or send_email call.

Lookup and Sending

On the same two-tool task, SFT #1 queries the sharing policy before sending. SFT-GRPO #1 attempts to send first, then queries and sends again after being blocked. Both succeed, but the timing of the first send attempt differs. The paired case in §6.1 gives the complete calls, tool returns, and per-trajectory judgments alongside the improvement on original combined requirements.

Two-tool task results

The two models perform as follows on the same 60 two-tool tasks:

Check SFT #1 SFT-GRPO #1
Task completed 50/60 50/60
Interaction signature match 30/60 30/60
Pre-write lookup condition satisfied 60/60 0/60
Premature action occurred 0/60 60/60

On these 60 email two-tool tasks, both models complete the same 50 tasks. However, SFT #1 satisfies the pre-write lookup condition on every task, while the model after continued GRPO satisfies it on none and acts prematurely on all tasks. The same 30 tasks also match the interaction signature under both models; the change is in action order.

In Chapter 3, expanded SFT training reduces both task completion and pre-write lookup on the two-tool tasks. Continuing GRPO from SFT #1 preserves their completion rate while losing the correct query order. Both forms of training improve performance on the original tasks, with deterioration on the two-tool tasks taking different forms.

Together with the cross-domain results in §4.1, this shows recovery on basic tasks in unfamiliar domains, with inconsistent adaptation to added action requirements.

We hypothesize that GRPO reinforces procedures effective on the original email tasks. Some of these procedures also apply to payments and scheduling, helping recover cross-domain completion rates. However, the original email tasks supply the sharing rules through the file lookup, so the model may increasingly tend to act directly after that query. When the rules move behind another tool, following the same order leads it to attempt a write before obtaining the necessary information. This could explain why cross-domain improvement and deterioration on email two-tool tasks occur together.

4.3 Adding Training Tasks for the New Tool

In the original tasks, retrieve_files returns file information together with whether sending is allowed and whether confirmation is required. The added tasks remove these two rules from the file response and return them through retrieve_sharing_policy instead. The model therefore needs an additional tool call to obtain information previously available from a single query.

We again start GRPO from SFT #1. Each of the 60 added tasks uses four request templates, producing 240 inputs. Combined with the original 768, this gives 1,008 inputs. We call the trained model SFT-GRPO #2.

After training, we evaluate the model on the original email tasks and two sets of 60 numerical-comparison tasks. In the two-tool numerical-comparison tasks, file size and sharing thresholds come from separate tools. In the single-tool numerical-comparison tasks, the sharing-policy tool returns these numbers together in one response.

Test tasks File lookup returns Sharing-policy lookup returns
Two-tool numerical-comparison tasks File size Approval threshold and hard sharing limit
Single-tool numerical-comparison tasks File information without size File size, approval threshold, and hard sharing limit

Neither test set appears in training. The added training tasks let the model obtain the rules directly from the sharing-policy tool; the tests require it to use the returned numbers to determine whether sending is allowed and whether confirmation is required.

The added training preserves original-email completion, with ten fewer trajectories matching the interaction signature. All four two-tool test results remain unchanged. When file size and thresholds are returned together, the model completes 49/60 tasks, with pre-write lookup again at zero.

Each test set contains a task asking the model to send a report to Zhang Wei. On these two tasks, SFT-GRPO #2 executes exactly the same actions:

Both trajectories attempt to send after the file lookup and obtain the sharing policy only after being blocked. They fit the hypothesis in §4.2 that completing the file lookup has become a cue to proceed with sending. Although the added training includes the sharing-policy tool, the same premature attempt persists in both numerical tests. Whether a tool appears in training and whether the model calls it in time when information is missing are two separate checks here.

Chapter summary

After continuing GRPO from SFT #1, the model completes all original email tasks and recovers performance on payment and scheduling tasks that preserve the original rules. At the same time, it loses its previously correct query order on the email two-tool tasks. Adding training tasks that require the sharing-policy tool leaves pre-write lookup at zero on both numerical test sets. Including this tool in the training tasks does not make the model call it at the required time under the new task requirements.
