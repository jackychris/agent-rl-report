Chapter 5. GRPO Starting from Instruct

5.1 Training from Instruct

We start GRPO directly from the initial Instruct model to examine whether reinforcement learning teaches it to follow task rules and transfer these capabilities to changed tasks. We call the trained model GRPO #1. Compared with Chapter 4, this route omits the preceding SFT stage.

Training uses the same 192 original email tasks, each with four request templates, giving 768 inputs. The model generates its own tool calls, and the evaluator scores the trajectories using the baseline reward from Chapter 2. Each batch contains 32 inputs, with eight trajectories sampled per input at temperature 1.0. We compute advantages from within-group rewards and update the LoRA parameters for 120 training steps.

The validation set uses the 48 tasks with changed people and files from Chapter 4. Each task uses six request templates, giving 288 inputs.

Original tasks and holdouts

We compare Instruct before training with GRPO #1 after training on the same evaluation tasks.

Training tasks (192) 156/192 → 176/192 72/192 → 168/192
Changed people and files (48) 41/48 → 44/48 30/48 → 42/48
Clarification–confirmation paired test (20) 18/20 → 20/20 9/20 → 20/20

Starting GRPO directly from Instruct yields 20 more successful training tasks and 96 more trajectories matching the interaction signature. Improvements also appear when people and files change, and all 20 clarification–confirmation paired tasks succeed. However, all 20 contain premature action. The model more often completes the request and matches the interaction signature while still violating action conditions.

The model queries the sharing policy on 58 tasks, always before the first relevant write. It omits the tool on the other two tasks. However, premature action still occurs on every task, and no task has all its write attempts pass the action-condition checks.

Pre-write lookup checks the order of the sharing-policy query and the first write. Premature action checks whether the conditions required for acting have been met. Querying the sharing policy first is one of these requirements, so the two checks can give different results.

Below is a complete saved sequence of tool calls.

retrieve_files({"query":"报告"})
→ retrieve_contacts({"query":"张伟"})
→ retrieve_sharing_policy({})
→ create_draft({
     "file_id":"report_target_1",
     "recipient_id":"contact_target_1"
   })
→ send_email({
     "file_id":"report_target_1",
     "recipient_id":"contact_target_1"
   })
→ finish({})

This trajectory queries the policy before attempting to create a draft and send the email. The draft attempt conflicts with the send intent and therefore fails the evaluator’s action-condition check even after a lookup. Across the 60 two-tool tasks, 28 trajectories receive the premature-action flag solely because of such intent mismatches, with the other checked conditions satisfied. The 60/60 premature-action count includes these intent errors.

On the original email tasks, SFT-GRPO #1 completes 260/260 and GRPO #1 completes 240/260, both above the initial Instruct model's 215/260. When the sharing rules move behind another tool, the former never queries the sharing policy before writing, while the latter does so on 58/60 tasks. The model with higher original-task performance performs worse on this lookup requirement.

SFT #1 originally satisfies the pre-write lookup condition on all 60 two-tool tasks; this behavior is lost during continued GRPO. GRPO trained directly from Instruct produces a different query order. The difference between these routes therefore involves the changes arising from the training starting point together with subsequent reinforcement learning.

We hypothesize that GRPO reinforces different behaviors from different starting points. Starting from SFT #1, the model may increasingly settle into sending as soon as it finds the file. Starting from Instruct, it more often continues seeking information when the sharing rules are missing. The original tasks provide the rules through the file lookup, so both approaches complete most tasks. The two-tool tasks change the information source, exposing the difference in how the models adjust their query order.

The sharing-policy tool directly returns whether sending is allowed and whether confirmation is required; the model does not need to compare file size with thresholds. The cue does not contain the sharing rules. The model must call retrieve_sharing_policy to obtain them. We separately count whether it calls the tool and whether the call precedes the first relevant write.

Both versions attempt to create a draft at step 2 and send at step 3. The environment blocks the calls for an intent mismatch and missing sharing rules, respectively. For agent-workflow design, source cues and execution checks serve different roles. In this example, the cue directs the model to the rules, while the environment's condition check blocks premature sending. Completing the request also requires the model to choose an action again after obtaining the rules.

5.2 Reward and Optimization Settings

We separately change the reward function and policy-clipping range to test whether these interventions improve action order. Both experiments compare against GRPO #1 on the original and generalization tasks.

GRPO #3: Penalizing Premature Action

We keep the training start and setup of GRPO #1 and add a premature-action penalty to the reward, producing GRPO #3. For the same trajectory, the score difference with and without the penalty is

Rpenalty(τ)−Rbaseline(τ)={−1,if premature action occurs and the hard gate does not fire,0,otherwise. R_{\mathrm{penalty}}(\tau)-R_{\mathrm{baseline}}(\tau) = \begin{cases} -1, & \text{if premature action occurs and the hard gate does not fire},\\ 0, & \text{otherwise}. \end{cases} Rpenalty​(τ)−Rbaseline​(τ)={−1,0,​if premature action occurs and the hard gate does not fire,otherwise.​

We use the hard-gate rule defined in Chapter 2. Multiple premature actions in the same trajectory still incur only one additional penalty point.

We hypothesize that the learned adjustments rely more on familiar training procedures and adapt poorly to the action conditions in the new tasks.

GRPO #4: Raising the Upper Clipping Bound

We keep the reward and other training settings of GRPO #1 and raise the upper probability-ratio clipping bound from 1.20 to 1.28, producing GRPO #4. This experiment tests whether relaxing the update constraint helps the model adapt to changed tasks.

where GRPO #1 uses u=1.20u=1.20u=1.20 and GRPO #4 uses u=1.28u=1.28u=1.28. Both use a lower bound of 0.80.

5.3 State Baselines and Random Seeds

We change the advantage calculation, constructing a baseline from facts marked known in the environment ledger before each action, then test whether this training preserves pre-write lookup.

Training starts from Instruct. The inputs come from the original email tasks. We adjust how often each task is repeated according to its success rate over multiple sampled trajectories, increasing the share of tasks on which both success and failure occur. This produces 1,500 inputs. Each batch contains 32 inputs, with eight trajectories sampled per input, and training runs for five passes and 230 steps. The three runs reuse the same dataset and vary the data-loading random seed.

Standard GRPO subtracts the group mean return from each trajectory's return. Here, we instead subtract a baseline calculated from the ledger before the action:

Dit=Gi−1.5mit. D_{it}=G_i-1.5m_{it}. Dit​=Gi​−1.5mit​.

Here, GiG_iGi​ is the terminal return of trajectory iii, and mitm_{it}mit​ counts resolved fields in the environment ledger before action ttt. For example, finding a file ID adds file_id; learning that external sharing is forbidden also adds one field, external_allowed=false. This counts resolved answers, whether they permit or prohibit an action. The coefficient remains fixed at 1.5.

For example, consider a trajectory with terminal return 9. An action preceded by two resolved facts has Dit=6D_{it}=6Dit​=6; another preceded by four resolved facts has Dit=3D_{it}=3Dit​=3. Actions within the same trajectory can therefore receive different return-minus-baseline differences.

During training, we divide these values by the standard deviation of the return-minus-baseline differences for all actions in the current batch:

Ait=DitσD+ϵ. A_{it}=\frac{D_{it}}{\sigma_D+\epsilon}. Ait​=σD​+ϵDit​​.

Here, ϵ\epsilonϵ is a small constant that prevents division by zero. Tokens in the same action-generation span share the same AitA_{it}Ait​. This calculation does not subtract the group mean, so equal returns across a task's eight trajectories do not necessarily produce zero advantages.

5.4 Choosing Actions from Returned Information

The WebShop visit reward makes the model open the designated subpage on almost every task, raising a further question: does it adjust its actions to the returned content? In Ask-or-Act, we make the returned rules determine whether sending is allowed and whether confirmation is required, then test this capability with paired tasks. We use the model trained with seed 1 in the previous section. Chapter 7 gives the actual comparison protocol and readings for the WebShop text-treatment experiment.

We construct three paired tests, each containing ten task pairs, for 60 tasks in total. Within each pair, the request, file, and contact are the same; the sharing policy or the user's confirmation reply differs.
