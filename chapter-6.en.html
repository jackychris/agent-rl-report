6.1 Behavioral Comparisons Across the Three Training Routes

Recovering base-task performance does not give the training routes the same generalization behavior. The paired trajectories below locate these differences.

Once the file size and both thresholds are available, the executor derives “sending allowed, confirmation not required,” enters these facts in its ledger, and uses them to check the send conditions. The policy response shown to the model still contains only the two thresholds; the model must combine them with the file size itself.

Here the change goes in the opposite direction. The trained model attempts to send before consulting the new tool, then queries after being blocked. Both models also request confirmation unnecessarily under this size condition. Lookup order changes, while unnecessary confirmation persists.

Across the 60 two-tool tasks, the models succeed on exactly the same 50 task IDs and match the signature on exactly the same 30 IDs. Pre-write lookup falls from 60/60 to 0/60, and premature action rises from 0/60 to 60/60. Improvement on the original combined requirements and deterioration under the new information source occur during the same continuation of training.

We hypothesize that continued training reinforces procedures effective on the original tasks. The new tool was absent from that training, and the model may become more likely to act immediately after retrieving a file. The respective roles of sampling preferences, reward selection, and other optimization processes in this change remain open questions.

Both trajectories end with exactly one confirmed booking for member_target_1 and retro_target_1. The second uses a group ID as a member ID; after the call is blocked, the simulated user supplies the correct member ID. The environment permits the question and accepts the subsequent booking, while the evaluator records the question as unnecessary and the earlier attempt as premature. The first trajectory's agenda clarification is also unnecessary.

Binding can be checked directly from the trajectories. Read owner_handle from the visible retrieve_groups return, then check whether a later retrieve_members call passes the same value as handle. This is true for the first trajectory and false for the second. The check compares the model-visible return with the later argument; the internal fact ledger describes environment state.

Among the 30 tasks that require this binding, SFT #1, SFT-GRPO #1, and GRPO #1 pass the returned handle on 30/30, 1/30, and 6/30 tasks; success is 28/30, 9/30, and 30/30. All three query the group in all 30 tasks. Their difference lies in subsequent use of the returned value.

For a booking service, success counts describe completion, while blocked attempts, subsequent retries, and requests for user clarification or confirmation describe the cost of getting there.

6.2 Generalization Differences in Querying and Rule Application

The two-tool tasks require the model to find the sharing-policy tool and combine file size with thresholds to decide how to act. To separate tool discovery from numerical judgment, we compare them with the rule-relocation tasks introduced earlier. Both require an additional call to retrieve_sharing_policy; the rule-relocation tasks directly return whether sending is permitted and whether confirmation is required, without numerical comparison.

Across 600 evaluations of the five models on the two task sets, none retrieves the sharing policy before writing. All 60 rule-relocation trajectories from SFT #1 match the interaction signature, yet none performs the required pre-write lookup.

The source cue does not change this order either. In §5.1, the number of tasks in which GRPO #1 calls the sharing-policy tool rises from 12/60 to 22/60, but all these calls occur after the first write attempt. The cue increases tool-call occurrence without moving lookup before action.

Chapter 4 adds tasks requiring the sharing-policy tool to training, yet pre-write lookup remains zero on both numerical test sets. Together with the source-cue experiment, this suggests that some models use the new tool for recovery after an initial send attempt. In Chapter 4's representative trajectories, the environment blocks a send with missing evidence, after which the model queries the policy and sends again. What they need to learn here is to decide when to act based on whether the necessary information is available.

Two of the three state-baseline seeds preserve correct query order. Across runs, original-task completion and query order under new information sources change differently.

6.3 Curriculum Generation and Evaluation

The preceding experiments changed rewards, optimization settings, and demonstrations. We also compared two ways of choosing training tasks: increasing the frequency of existing tasks and using an LLM to generate new ones. The question is which tasks and behaviors benefit from the new curriculum.

Reweighted and Synthetic Curricula

Both runs start from the initial Qwen3-8B Instruct model. The reweighted curriculum uses the original 192 email training tasks. Eight samples per task determine its repetition count. For the 61 tasks with both successes and failures, each request template appears four times; for the other 131 tasks, each template appears once. Across four templates, this gives 61×4×4+131×4=1,50061\times4\times4+131\times4=1,50061×4×4+131×4=1,500 training inputs. Task rules and scoring remain those of the original environment.

For the synthetic curriculum, DeepSeek-v4-flash proposes email-task variants from execution branches and specifies required actions, forbidden actions, and terminal outcomes. The variants use parameters of the existing environment, such as additional candidate contacts, changed sharing rules, or retrieval faults. The model then generates a solution, which code checks against the accompanying rules. The final dataset contains 10 synthetic task entries whose solutions pass the checks, each repeated 92 times, plus 580 records sampled from the original training inputs: 1,500 rows in total.

Each synthetic training prompt contains only the system message and task request. Task-construction parameters, scoring rules, and generated solutions are stored as training metadata. GRPO samples fresh actions for these tasks; the completed curriculum uses the accompanying rules to score them.

Both curricula receive five epochs of GRPO, totaling 230 steps, with 32 inputs per batch and eight rollouts per input at temperature 1.0. Appendix C.1.5 gives the remaining settings. This comparison changes both training content and the scoring rules for synthetic tasks; its objects are the two curriculum recipes.

Fixed Scoring Rules for Synthetic Tasks

The initial synthesis procedure asked an LLM to judge whether each solution was correct. We resubmitted 46 previously accepted trajectories to the same DeepSeek-v4-flash model. Two repeat judgments accepted only 13/46 and 12/46. DeepSeek-v4-pro accepted 35/46. Each fraction counts how many previously accepted trajectories were accepted again.

The completed synthetic-curriculum run instead executes scoring rules supplied when each task is generated. For example, one synthetic task with sharing forbidden requires contact and file retrieval, clarification of file identity, and termination. Sending, drafting, and requesting confirmation are forbidden. Scoring checks these requirements and whether the terminal outcome is a send, a draft, or no write.

The synthetic reward is a weighted mean of binary checks. Branch order, terminal outcome type, and absence of blocked actions each receive weight 2; the remaining checks receive weight 1. The order check compares only non-clarification actions. Clarification is scored separately by occurrence, and terminal comparison distinguishes only send, draft, or no write. A generated solution is retained only if all checks pass; training uses the weighted score directly. Fixed rules make repeated scoring of the same trajectory deterministic; whether those rules fully express the task depends on their content. The early repeat-judgment experiment and the completed curriculum therefore use different scoring procedures.

Evaluation on Original and Synthetic Tasks

We evaluate both curricula on 68 fixed tasks from the original email suite and 13 separately generated task records. The former use the original deterministic evaluator; the latter use their accompanying scoring rules. These 13 records derive from five seed tasks, four of which also generated the 10 synthetic training records. Comparing the combined seed, variant index, construction parameters, and scoring rules finds no exact record overlap between training and evaluation, although they share seed tasks.

Six of the 10 synthetic task entries are derived from two tasks among these 68. We therefore use the 68 tasks as a fixed reference set whose task sources partly overlap with those of the synthetic curriculum.

Evaluation set Reweighted curriculum Synthetic curriculum
68 fixed tasks from the original suite 64/68 63/68
13 separately generated task records 0/13 6/13

The synthetic curriculum passes more generated tasks and completes one fewer original fixed task. Both task content and scoring differ between the sets. The results show that the observed curriculum benefit depends on what is evaluated.
