Chapter 7. Visit Rewards and Content Responses in WebShop

7.1 WebShop Tasks, Rewards, and Text Treatments

In our WebShop experiments, we add a reward for visiting product subpages, aiming to encourage the model to obtain information before buying and use it to choose products that better match the user's requirements.

Page-visit frequency measures whether the model learns the retrieval action. The content-treatment experiment changes page text and compares purchase fields and action sequences. We first define the fields, then interpret the results accordingly. We also decompose attribute scores for purchased products to locate matched attributes across pages.

Task and terminal score

This section compares three GRPO models trained from the initial Qwen3-8B Instruct model to step 75. The first uses only terminal reward. The second adds a 0.08 page-visit reward. The third grants that visit reward only when the final purchase receives full task reward. These are separate training runs used to compare how the reward condition affects retrieval behavior.

WebShop simulates a shopping website. After receiving the user's purchase requirements, the model starts from the search page and operates the website through text commands. The system executes each command and returns the page content to the model.

Command Effect
search[query] Search for products using a model-generated query
click[B0XXXXXXXX] Open the corresponding product's detail page
click[option value] Select a variant such as color or size
click[description], click[features], click[reviews], click[attributes] Open a product subpage for additional information
click[back to search], click[< prev], click[next >] Go back or change page
click[buy now] Purchase the current product and end the task

The model generates the query in search[...] and selects the target of click[...] from the clickable items shown on the page. In this experiment, each task allows at most 15 actions and ends after a purchase or when the action budget is exhausted.

WebShop computes the terminal score from the purchased product and selected options.

Terminal score=Matched attributes+Correct options+Price scoreRequired attributes+Required options+1×Type-match coefficient. \text{Terminal score} = \frac{ \text{Matched attributes}+\text{Correct options}+\text{Price score} }{ \text{Required attributes}+\text{Required options}+1 } \times\text{Type-match coefficient}. Terminal score=Required attributes+Required options+1Matched attributes+Correct options+Price score​×Type-match coefficient.

The price score is 1 when the price does not exceed the user's limit and 0 otherwise. The type-match coefficient takes values 0,0.1,0.5,10, 0.1, 0.5, 10,0.1,0.5,1 according to title, category, and query matching. The exact rules appear under “WebShop Type-Match Coefficient” in Appendix B.1.

For example, the user requires two product attributes, one option, and a price limit, giving four requirements. If the purchased product matches one attribute, the option and price are correct, and its type fully matches, the score is 3/43/43/4.

Visit reward

We reward visits to four product subpages: description, features, reviews, and attributes. Opening any one of these subpages before buying the product satisfies the visit condition. Repeated visits or visits to multiple subpages count only once.

The visit and purchase must concern the same product. For example, reading product A's description and then buying product B does not earn the reward. The model must visit B's subpage before buying B. Without a completed purchase, there is no visit reward.

Let ppp denote the visit-condition measure, calculated from purchases satisfying the condition above.

p=Purchases satisfying the visit conditionPurchases. p=\frac{\text{Purchases satisfying the visit condition}}{\text{Purchases}}. p=PurchasesPurchases satisfying the visit condition​.

If no purchase occurs, p=0p=0p=0. WebShop usually ends after the first valid purchase, so ppp normally takes one of two values: 1 if the model visited that product's subpage before buying it, and 0 otherwise. Page openings are counted separately to check for repeated visits.

R=G+λp. R=G+\lambda p. R=G+λp.

Evaluation methods

Task evaluation runs each model once per task and saves terminal scores and page-visit information. Trajectory replay re-executes saved actions to check whether visits return nonempty content. The content-treatment experiment runs separate text conditions for the same task and saves action sequences and purchase fields. Product-score decomposition examines the products actually purchased to locate matched attributes in titles and subpages.

Content-treatment experiment

The script starts a separate run from the initial page for each task and condition. It does not save an intermediate state and branch into two continuations. Every qualifying observation is processed, so a trajectory may receive treated content more than once.

Condition Treatment
Reference, null Replace Rating: N.A. with Rating: 4.3; otherwise replace the first Rating: with Rating: 4.3 —, retaining the original rating that follows
price Set the detail-page price to three times the user's budget
note Append a product-mismatch statement to detail pages
desc Append information conflicting with the request to subpages
note_sub Append a product-mismatch statement to subpages

The script selects null as a reference because it treats star ratings as outside the task requirements; this condition still changes model-visible text. A comparison with a subpage condition can therefore differ at an earlier detail page. For each pair, we compare action sequences, target products, and treatment counts to check whether the runs already differed before the treatment.

The desc condition fills the templates This product is NOT {attributes}. and It is not available in {options}. with the task's attributes and options. If both are absent, it falls back to an over-budget or generic mismatch statement. In contrast, note and note_sub always append NOTE: This item does NOT match your request.; only their placement differs. Subpage treatment is triggered when the preceding click is description, features, or reviews, excluding attributes.

The script assigns each run's target from its first call of the form click[b0…]. Subsequent page treatments do not check again that the current product is this target. The saved bought_target field is true when the environment reports termination and the last such product click in the action sequence points to that run's target. This Boolean indicates only whether this condition holds; the full identity of the final purchased product is absent from this Boolean field.

We pair runs by task ID, retaining tasks with evaluation outputs under both conditions and fired=true in both runs. This field means that page text changed at least once. We calculate

Purchase-field change rate=Pairs with different bought_target valuesPairs with text treatment triggered in both runs. \text{Purchase-field change rate} =\frac{\text{Pairs with different bought\_target values}} {\text{Pairs with text treatment triggered in both runs}}. Purchase-field change rate=Pairs with text treatment triggered in both runsPairs with different bought_target values​.

Eligibility depends on whether each run reaches a treated page. Section 7.2 separately compares purchase Booleans, target products, and action sequences across the paired runs.

Attribute-score decomposition of purchased products

For the product actually purchased in each replayable trajectory, we check whether requested attributes occur in its title, Description, or BulletPoints. The att_subpage_only field counts requested attributes absent from the title but present in Description or BulletPoints. These are attributes already matched by this purchased product.

For each purchase trajectory included in the decomposition, we compute

Subpage-matched attribute share=Requested attributes matched in Description or BulletPoints but not the titleRequired attributes+Required options+1. \text{Subpage-matched attribute share} =\frac{\text{Requested attributes matched in Description or BulletPoints but not the title}} {\text{Required attributes}+\text{Required options}+1}. Subpage-matched attribute share=Required attributes+Required options+1Requested attributes matched in Description or BulletPoints but not the title​.

For example, two attributes, one option, and a price limit give four scoring components. If one requested attribute of the purchased product matches only in those subpage texts, the share is 1/41/41/4. The calculation omits the product-type coefficient and describes a share of scoring components.

We retain tasks with a score decomposition whose replayed score matches the saved terminal score, then calculate the mean, median, and zero count. This quantity describes the attribute-score composition of the products actually purchased and varies with those products and the replayable task set. Benefits from switching products, rejecting unsuitable products, or changing options after reading are forms of information value outside this decomposition.

7.2 Training Results with Visit Rewards

Page visits and returned content

We compare three training schemes: terminal reward alone, an added visit reward, and a visit reward given only for full-score purchases. Each model runs once on the same 500 tasks, yielding 500, 499, and 498 trajectories, respectively, that can be parsed and produce an environment outcome. The table uses each model's valid task count as its denominator.

Added visit reward 498/499 (99.8%) 221/499 (44.3%)

Adding the visit reward raises page visitation from 18.8% to 99.8% and task success from 42.8% to 44.3%. Restricting the bonus to full-score purchases still produces 99.4% visitation, with task success at 41.2%. Both reward schemes make the model visit a subpage before almost every purchase, while task success changes much less.

Actions after a page visit

We examine whether the model continues comparing other products after visiting a subpage, to understand the role of retrieval in the purchase process. After training, we evaluate the model trained with terminal reward only and the model trained with the full-score gate, sampling eight T=1.0T=1.0T=1.0 rollouts per task. The 500 tasks yield 4,000 and 3,987 valid trajectories, respectively.

We count clicks whose targets match the product-ID format to check whether the model clicks a product after visiting a subpage. The script identifies a sequence of ten lowercase letters or digits inside click[...] as a product ID, so it may also count option values with the same format. The table separately records whether such a click occurs and whether it targets a previously unseen ID. Both rates use trajectories that visited a rewarded subpage as their denominator.

The environment also directly records how many products the model examines. We use this record to count trajectories that examine exactly two products.

The model trained with the full-score gate visits subpages on 99.6% of trajectories. Among these visiting trajectories, only four contain a click matching the product-ID format after the first visit, and two of those click a previously unseen ID. The model rarely clicks other products after opening a subpage.

Mean actions per trajectory rise from 5.58 to 7.75, an increase of 2.17, close to the two actions needed to open a subpage and return to the product details. The two models have mean terminal scores of 0.711 and 0.712. The additional actions are not accompanied by an appreciable score increase.

The model trained with the full-score gate commonly follows this action sequence.

open product details
→ view rewarded subpage
→ return to product detail
→ buy the same product

Subpage visits occur mainly in the final steps before purchase, with little further browsing of other products afterward.

Evidence on Visitation and Content Use

The visit reward makes pre-purchase subpage visits nearly universal, and replay confirms that they usually return nonempty content. Task success changes much less than visitation, while the full-score-gated model usually visits near the end of its purchase procedure.

The text-treatment experiment compares purchase-field responses across conditions. It does not establish the stronger claim that the model learned retrieval without learning to use information. The attribute decomposition describes matches in purchased products, leaving the benefit of reading before product selection unmeasured.
